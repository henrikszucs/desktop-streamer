# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Desktop Streamer — an open source remote desktop / screen sharing application (web + Electron client, Node.js server). Very early stage; the architecture is actively being restructured, so verify a module against its source before trusting an assumption about it.

## Commands

`npm run server` and `npm run uninstall` are the only scripts; both accept `--help`, which is the authoritative list of their flags (`npm run server -- --help`). Arguments after `--` are forwarded. One rule covers every option that takes a value: a **short** option takes its value as the next argument (`-c ./conf/config.json`), a **long** one joined by an equals sign (`--configuration=./conf/config.json`). `getArg` in `common.js` is a plain reader and the caller names the form it wants (`isKeyValue`, `isInline`); `checkArg` beside it is what holds the CLI to the rule, refusing the wrong form by name at startup rather than letting it fall through to a default nobody asked for. It also catches what `getArg` cannot see on its own - a short option with nothing behind it, or with the next option behind it, where `-c --compile` would be read as a path called `--compile`.

`npm run uninstall` (`src/uninstall.js`) is the cleanup: it removes `package-lock.json`, `node_modules` and the contents of `./tmp` (the folder and its placeholder stay), and with `--bin` the contents of `./bin` too. It is what to run before a fresh `npm install` when the native addon has to be rebuilt.

`npm test` runs `tests/**/*.test.js` through Node's built-in runner (`node --test`, no dev dependencies — keep it that way). One file per area: `accounts`, `api`, `appname`, `assets`, `building`, `clipboard`, `common`, `conf-public`, `config`, `cursor`, `enhance`, `frame`, `http-path`, `joins`, `localization`, `login`, `mail`, `pairing`, `relay`, `rooms`, `stream-ffmpeg`, `zip`. `tests/frame.test.js`, `tests/stream-ffmpeg.test.js`, `tests/enhance.test.js`, `tests/clipboard.test.js`, `tests/cursor.test.js` and `tests/login.test.js` are the six client tests: `src/client/web/src/room/frame.js` and `src/client/web/src/room/stream-ffmpeg.js` are pure and run under Node, the pure part of `src/client/web/src/room/stream-enhance.js` (the presentation schedule and the ONNX shape patch, checked against the mock graphs under `media/models/`) runs there too, `src/client/web/src/room/cursor.js` runs whole under Node because the host's pointer is packed into a PNG written by hand over `CompressionStream` rather than through a canvas - which is also what lets the same file check `pictureBox` from `stream-input.js`, the letterbox mapping the peer's clicks and the pointer drawn over them share, and `src/client/web/src/room/clipboard.js` runs whole behind a fake shell clipboard - two synchronous calls are all either shell gives it, so what is worth sending, what is not worth sending twice and what becomes of a refused write are all provable under Node. `tests/login.test.js` is the one that runs a **UI module**, and the only one that does: `ui/management/login/index.js` imports and instantiates under Node because nothing in it touches the document until `mount()`, and `login()` is a function over `ctx` — so a fake snackbar and router in place of the shell are enough to hold the screen to what the button cannot say for itself, that a refused sign-in is *told* to the person, as an error, in a line the dictionary actually holds in every language. `tests/relay.test.js` is the one that runs the whole WS stack in process: it hands `serverWS.clientConnect()` a socket that is two function calls rather than a network, puts a real `Communicator` at each end, and pairs two clients through the real dispatch — which is how the relay is proved to carry a message from one machine to the other. Both ends have to `sideSync`/`timeSync`, as they do over a real socket. The tests covering build output (`tests/assets.test.js`) skip themselves unless `./tmp/web` holds a build, so run `npm run server -- --compile --exit` first to exercise them. There is no linter and nothing type-checks. `dev/rollup/conf.mjs` is an ad hoc helper for vendoring third-party packages into a `libs/` folder, never part of a normal run.

`.claude/skills/beercss/` is the class vocabulary of the beercss build vendored under `src/client/web/libs/` — load it before writing or changing markup under `src/client/web`. `.claude/settings.json` allows the read-only git commands and denies the ones that move history, so commits and pushes are the user's.

The default config path is `./conf/config.json`; `conf/config.example.json` is a valid SQLite-backed starting point, and `conf/` is gitignored apart from it.

`onnxruntime-web` is **not** a dependency either: the three files the client needs (`ort.all.min.mjs`, the JSEP loader and its 26 MB `.wasm`) are vendored under `src/client/web/libs/onnxruntime/` from the 1.29.0 package, since the client has no bundler and the runtime fetches its WebAssembly by URL. `ajv`, `uglify-js`, `ws` and `knex` are imported directly; `better-sqlite3` and `mysql2` are imported by knex as the driver the configuration names, and `better-sqlite3` is why a plain `npm install` builds a native addon. `nodemailer` is imported by `ws/mail.js` alone, for the account-deletion e-mail. **A configured database that cannot be reached now fails the boot**, where it used to be validated and ignored: `ws/database.js` is what the remembered joins and the accounts live in. `electron` is deliberately *not* a dependency: the shell runs inside the prebuilt dist from `./bin`.

## Architecture

ESM (`"type": "module"`) throughout. The one exception is `src/client/electron/main.js`, which stays CommonJS because Electron loads it directly — `building.js` minifies that folder in script mode for exactly this reason.

### Server (`src/server/`)

`server.js` is a thin CLI entry: parse flags → `loadConfig` → `compileClients` → start HTTP → start WS → install SIGINT/SIGTERM handlers. Each stage prints a `doing...    done/failed/skipped` line to stdout; keep that reporting style when adding a stage. Both servers are singletons imported as instances, and shutdown stops WS before HTTP because WS may be an upgrade on the HTTP server's own listener.

- `config.js` — the Ajv (draft-07) JSON Schema is the source of truth for every accepted config field. Cross-field rules the schema cannot express live in `checkConstraints` (port collisions — WS may share the HTTPS port but nothing else may collide; `http.remote` and a local `ws` section are mutually exclusive). `loadConfig` resolves the SQLite path and **replaces `key`/`cert` paths with their file contents**, relative to the config file's own directory, so downstream code holds PEM text, not paths. `http` takes an optional `appearance` — the application `name` keyed by language (the tab title and the desktop window and tray title in the client's language, the desktop auto-launch entry in English or else the first given; with none, the client dictionary's `main.name`), a `color` (`#rrggbb`) and a `theme` (`dark`, `light` or `auto`), each optional — which reaches the client through `index.json` as the colour and theme it starts with and a settings reset goes back to (the client writes a default into IndexedDB the first time it reads it, so a client that has already run keeps what it stored until it is reset). `http` and `ws` each take an optional `proxy` (`domain` + `port`, and on `http` an optional `redirect` port that `checkConstraints` refuses without an `http.redirect` to stand in front of), the address a client reaches that server at when it is not the one the socket is bound to: `getPublicAddress(conf, section)`, `getPublicWsAddress(conf)` and `getPublicRedirect(conf)` beside them are the one place that rule lives, and everything client-facing goes through them — the addresses `buildConfFile` compiles into `index.json`, the `Location` of the HTTPS redirect, the domain the account mail names the server by, and the `Available` and `Redirect` lines of the boot (the bound address is printed under each as `Listening` when a proxy hides it — `getPublicRedirect` answers `null` where a proxy was given no `redirect` port, since a public port nobody named is not one to guess, and the bound one is reported alone as before). `getPublicWsAddress` keeps the fallbacks the client conf always had — `http.remote` first, then the ws section's own proxy, then the *public* `http` host, and the whole public `http` address when the two share a port, since that is one listener behind the proxy. A `ws` section **requires** `domain`, `port`, `key`, `cert`, `database`, `webrtc` and `permissions` (the five permission flags all carry schema defaults, so an empty `permissions: {}` is enough); `ws/database.js` is what connects to the database. `ws.email` and `ws.auth` are optional but each requires the other (a schema `dependencies` rule — sign-in without a mail transport could never delete an account, and a transport without sign-in has nothing to mail): `auth.google.clientId` reaches a client through `buildPublicConf` and is what a credential is checked against in `handlers/accounts.js`; `email` is what `ws/mail.js` builds the SMTP transport from, and it is verified at boot — a transport that cannot sign in fails the boot the way an unreachable database does. A `ws` section that shares the HTTPS port likewise still has to carry a `key`/`cert` pair that is never used, because the HTTP server's listener is the one the upgrade is added to.
- `http.js` — a singleton `ServerHTTP` instance (exported as the instance, not the class). Serves `./tmp/web` and `./tmp/desktop`. Two request handlers: a streaming one, and a cache one chosen when `http.cache` is configured; both answer through the same `isRoutePath`, `isNotModified` and `fileHeaders`. The SPA fallback to `index.html` is for **routes only** — a path with a file extension, or one under `/src/`, `/ui/`, `/libs/` or `/media/`, 404s instead, or a mistyped `import()` specifier would arrive as HTML and fail with an opaque MIME error. Files carry `Cache-Control: no-cache` and a quoted `ETag`, and a matching `If-None-Match` (or `If-Modified-Since`) is answered 304. The cache is frequency-based, not LRU: a rolling access window re-scores every file by `accesses / size` every few seconds and swaps buffers in and out under the byte budget.
- `ws/` — the realtime/signaling server, split so that adding a call never means growing one file. Beside the dispatch and the handler groups it holds three files that are not either: `ws/database.js` (the knex connection, the tables created on first boot — each checked on its own, so a database from the joins-only build grows the account tables at the next boot — and the pool closed in `stop()`), `ws/mail.js` (the nodemailer transport built from `ws.email` and verified in `start()`, kept as `server.mailer` — `null` when the configuration names none — and closed in `stop()`; the one mail it sends is the delete key, its lines from `src/server/localization.json` read through `src/server/localization.js`, with `{app}`, `{domain}` and `{key}` substituted, in the language the client asked for or English) and `ws/notify.js` (`push`/`notify`/`notifyAll`, and `ANSWER_TIMEOUT` — the window a person has to answer, which both flows that ask one draw a bar against). `ws/ws.js` holds `ServerWS` (exported as the instance): the socket lifecycle — `start`/`stop`, a per-connection session id (`generateSessionId`, unique among the live `clients` Map), and the `Communicator` a connection is wrapped in — plus the process-wide state the handler groups share and never own: the `pairs`, `rooms`, `joins` and `accounts` Maps, and the `db`, `auth` and `mailer` that `start()` builds (database, then `createAuth`, then the transport, each its own `doing...` line). `ws/api.js` is the dispatch: it merges the group tables into one `type` → handler Map (throwing at import time if two groups claim one type), validates that an incoming message is an object with a string `type`, and calls the handler with a single `ctx` — `{message, messageObj, sessionId, server}` — so a handler's signature does not grow as the protocol does. `ws/handlers/<group>.js` is one file per group of calls, each exporting its own functions plus a `handlers` table of the types it answers, which is the module's default export. Today: `handlers/conf.js` (`conf-get`, and `buildPublicConf` that builds the answer once in `start` — ICE servers, the `permissions` block and the public auth client ids, never key material, SMTP credentials, OAuth secrets or database settings; the browser client stays offline until this one answers) `handlers/connection.js` (`ping`, `session-get`) and `handlers/pairing.js` (`pair-create`, `pair-delete`, `pair-request`, `pair-accept`, `pair-reject` — the six digit connection code a host hands out and the one join attempt it introduces, held in the `pairs` Map of `ws.js`). `pair-accept` carries the two flags the host ticked (`remember`, `unsupervised`) and answers with the join they made, each side told its own code and never the other's. A pair is `{hostSessionId, peerSessionId, answerTimeoutId}` and the client state Map holds the code the connection is in, whichever side of it that connection is; every exit — the delete call, an answer, the answer timeout, either socket closing — goes back through `removePairCode`/`releasePeer`, which is what keeps a code from being held for the life of the process. **A code has no clock of its own**: it stands while the host is offering it, since the dialog that shows it is the thing holding it open, and what replaces one is a refusal rather than an expiry. The only timeout in the group is the one on an answer. **The pairing calls are the first ones the server answers by talking to a *third* socket**, so this group also holds `push`/`notify` and the five server-initiated types: `pair-request` and `pair-cancel` and `pair-code` to the host, `pair-accept` and `pair-reject` to the peer. Two rules are worth keeping: a request is *told* to the host rather than confirmed with it (a sharing host is a tab somebody switched away from, and a throttled acknowledgment must not hold up the one waiting — an undeliverable push ends the request instead), and one code carries one attempt at a time, so a second peer is answered `busy` rather than queued behind a dialog. A refused code is replaced (`renewHostCode`) and the host is told the new one, so a number somebody just tried is worth nothing to them twice; a peer that merely gives up leaves the code alone, because the host decided nothing. The `conf-get` answer opens with `version`, the live `getVersion()` of the process answering, so the client checks its own build against the server on the one call it already waits for — there is no separate version call. `permissions` answers `guestAllowShare`, `guestAllowJoin`, `isAuth` (any sign-in at all) and `isGoogleAuth` for every client whether the config sets them or not, so the client gates features on the answer rather than on a default of its own; the `pairing` block beside it carries `answerTimeout` — the one clock of the pairing flow is the server's, and a client that is handed it draws a bar that means something instead of a spinner that does not; `guestAllowRelay` is answered beside them, since a fallback that is not there must not be waited for; `userRegister` (whether an unknown account may be created at sign-in) and `userRegisterRelay` stay server-side. `handlers/rooms.js` is what an accept leaves the two sockets *in*: the `rooms` Map of `ws.js` (`Map<roomKey, {hostKey, peerKey, hostSessionId, peerSessionId, joinId}>` — **one room, two keys, so the room is in that Map twice**), made by `pair-accept`, `join-accept` and the unsupervised `join-request` alike, and the two calls carried across it - `room-signal` (one SDP or candidate to the other socket, opaque to the server, an object of at most 16 KB), `room-data` (the same relay, *answered*, for a small message a caller wants confirmed - 64 KB, because a JSON message is one frame) and `room-leave`. Beside the three there is **one route that is not a call at all**: a binary message. The communicator splits an ArrayBuffer into packets and reassembles it, and does none of that for JSON, so anything that is not small travels as a frame - `[kind][10 byte room key][payload]`, kind 1 for bytes and 2 for a JSON payload - which `api.js` hands to `roomFrame` because there is no `type` field in it to dispatch on. The frame is forwarded one way and unanswered, since a stream cannot stop for an answer per frame, and the only thing rewritten on the way is the key in its header (see below). **There is no size limit on it**: 16 MB crosses in ~600 ms in `tests/relay.test.js`'s stack. Three things it settles. **A room is not a join**: a pairing that was not remembered leaves no join behind, so a relay keyed on one could carry nothing of the connection it just made; the room is memory only and dies with either socket, since a half-negotiated connection is worth nothing. **Both sides are told rather than answered**: `room-open` carries the key *and* which side each socket is - the host of an unsupervised join is never asked anything, so there is no answer to put a key in - and which side it is decides who offers (the peer does); it also carries `isNew`, true only from `pair-accept`, since only the server knows whether a room is a connection made this moment or a remembered device back, and the host's shell moves for the first alone. **The two sides do not share a credential**: `createRoom` mints a `hostKey` and a `peerKey`, tells each socket only its own, and registers the room under both; every room call carries the caller's own key and `heldRoom` asks two questions of it - is this a key this server handed out, and is the socket presenting it the side it was handed to - so the far end of a room holds nothing it could act with, and a key that gets out (a log, a screenshot, a client that keeps more than it should) can only ever do the half its holder was already doing. Because a key is a side, everything carried across is **re-addressed**: `room-signal`, `room-data` and `room-close` go out under the *receiver's* key, and `roomFrame` writes the receiver's key over the sender's in the ten header bytes in place - the payload behind them is not touched and nothing is copied, but the bytes that arrive are no longer the bytes that were sent. **The server holds nothing between two signals**: it is one message per call rather than the loop `dev/plans/` describes, so there is no held-open conversation to bound. `guestAllowRelay` gates **the relayed payload in both of its forms** - the `room-data` call and the binary frame, which is the one a client actually streams over - and nothing else: the schema calls it media data transfer, so it is what pays for the fallback, while the negotiation every connection needs (`room-signal`) is never gated - a flag that defaults to false would otherwise mean no guest could ever connect. It is answered to the client in `permissions` as well, since a fallback that is not there must not be waited for. **The permission is the connection's, answered once**: `clientConnect` writes `isRelayAllowed` into the client state when the socket is taken and `isRelayAllowed()` in the group reads it from there - the relay carries a message at a time, so a check that walked the configuration (or read a row) would cost more than the thing it guards. Nothing re-reads it while a connection is live; when accounts land, sign-in is what fills that one slot from the user's row. `handlers/joins.js` is what a host that ticks **remember** leaves behind: the `joins` row that outlives both sockets (`join_id`, the two codes, the names, `peer_user_id`, `is_unsupervised`), and the calls a device that comes back uses — `join-connect` (present a code, be reachable on it), `join-list` (who is online, for the two screens), `join-sync` (the devices of the account the socket is signed in as, peer codes included — `not-signed-in` for a guest), `join-rename` (what this side calls the other one), `join-request`/`join-accept`/`join-reject` (the same accept-or-reject as the pairing, on a pairing already made — `join-request` pushed to the host's sockets, `join-accept`/`join-reject` to the asking peer, and `join-cancel` to the host when the peer stops asking or its socket goes, so a request dialog is never left open for nobody) `join-delete` (either side forgets the other for good) and `join-disconnect` (the caller off every join it presented, or only the `joinIds` it names, rows untouched — what a guest signing out calls bare, and what a client switching accounts calls with the old account's devices so its shares stay reachable). Five things are worth keeping straight. **A join is owned on one side only**: `pair-accept` writes the peer socket's `userId` into `peer_user_id` (`""` for a guest) and `host_user_id` stays empty, because a share is the machine's and a device is the person's — the account is the credential for its devices (`join-sync` hands them to any client it signs in on), the code is the credential for a guest's, and `dropJoin`/`removeUserJoins` is what the account `delete` in `handlers/accounts.js` calls so the devices go with the account and each host is told `join-remove`. Neither column carries a foreign key (the table is only ever created), which is why that deletion is explicit. Which of the two codes a socket presents is still what decides the side it is on. **`server.joins` is presence, not truth**: the row is the join, the Map holds only the sockets currently reachable about one and is dropped when the last leaves, and a side that arrives or leaves is pushed to the other as `join-online` - only on the edges, since a second window of a device that is already there changes nothing, so a client draws who is present rather than polling `join-list` for it. **`is_unsupervised` is the whole difference** between a device that makes the host answer a dialog and one that walks straight in — `join-request` returns `{"isAccepted": true}` without notifying anybody for the second. **A name belongs to the side that gave it**: `peer_name` and `host_name` are separate columns, `join-rename` writes only the caller's own and pushes nothing, and `join-connect` reads that same one back — so the name lives on the row rather than only in the client, and a device presenting the code again is handed what it called the other one. A refused *join* stands, unlike a refused pair code: the peer may ask again, since the host already agreed to remember it. `handlers/accounts.js` is who a connection is when it is somebody: the `users` row (`user_id`, `email`, the two names, `is_relay_allowed`), the `users_google` link keyed on Google's `sub` — never on the e-mail, which a person can change — and the `sessions` row (`session_id`, the secret `session_key`, `expire`, `last_used`, `ip_address`, `user_agent`) a device keeps to come back without Google. Eight calls: `login-google` (a credential from Google's button, checked at Google's `tokeninfo` endpoint and then against three things it cannot check for us — `aud` is *this* client id, the e-mail is verified, `exp` is ahead — answered with the session and the profile; an unknown person is made when `userRegister` allows it and refused `register-disabled` when not — but an address that is **already a `users` row with nothing behind it** is *claimed* rather than made, whatever `userRegister` says: the row is what the person signs in on and the credential fills in whatever it left empty, which is how an organization seeds its own address list and leaves registering off on a domain anybody can reach, while an address that is already somebody's Google account is `email-taken`; a `sessionKey` sent along that is a live session of the *same* user is refreshed and answered back rather than a second row written, as is the session the connection is already signed in on — one device, one row), `login-session` (the key presented again — the client does it on **every** socket, because the server holds who a socket is for that socket alone — and the expiry pushed out another `SESSION_LIFETIME`, expired rows swept on the way), `login-guest` (the connection is the guest again, the row left standing), `logout` (a session ends — the caller's own or, given a `sessionId`, another of the same user — on every socket presenting it, the ones that did not ask pushed `logout`), `user-update` (the two names; the e-mail is Google's to say; the user's other sockets are pushed `user-change`) `session-list` (every live session, the caller's marked `isCurrent`, the key never among them), `sessions-revoke` (the recovery: a fresh credential — from anybody, a guest most likely — ends **every** session of the account it names and starts none, every socket that was that person is a guest again and pushed `logout`, the caller answered instead; a hijacked session that keeps ending new ones would otherwise win, since `logout` is a signed-in socket's call), and the two halves of deleting the account: `delete-email` (a `delete` row — `delete_id`, `user_id`, `session_id`, the unique `delete_key`, `expire` 24 hours out, `created` — and the key mailed to the address on the users row; **one code stands per account**: asked again from the same session it mails the same key again with `created` moved up, asked from another session it replaces the row, so two codes are never good at once; answered `mail-disabled` without a transport, `too-soon` within `DELETE_COOLDOWN` of the last mail, and `mail-failed` when SMTP refuses — a new row is removed again, since a key that was not delivered is not a key, while one mailed before stands) and `delete` (the key back, matched against the caller's user **and account session** — the row carries the `session_id` that asked and cascades with it, so a key is only good on the device it was mailed for and a logout drops it; a match deletes the users row and the foreign keys take the Google link, the sessions and the delete row, every socket that was this person is a guest again and pushed `logout`, the caller answered; anything else is `invalid-key`, expired rows swept on the way). Four things are worth keeping straight. **Verification is swappable**: `createAuth(conf)` in `start()` builds `server.auth` — `verifyGoogle` and the two register rules — and a test puts a verifier of its own there, which is how `tests/accounts.test.js` signs in without Google. **`server.accounts` is presence**: `Map<userId, {sessionIds, picture}>` holds a user while a socket is signed in as them, and the picture is fetched once per online account with `httpsGetImage` and handed on as a data URI, so a bar that draws it on every screen never fetches from Google itself. **The relay permission is the user's**: `attachAccount` writes `is_relay_allowed` into the connection's `isRelayAllowed` slot and `detachAccount` puts the guest's back — the one slot `clientConnect` filled from the configuration, read once per sign-in and never per message. **A name the user gave is theirs**: a later `login-google` fills only an empty name from Google and never overwrites one. A join is owned by the peer's account (see `handlers/joins.js`), so `delete` drops the devices of the account through `removeUserJoins` before the users row goes.

Every server-initiated type the client accepts is listed in `PUSH_EVENTS` of `src/client/web/src/server.js` — seventeen today, across the four groups — and a push of a type not in it is logged by the client rather than dispatched, so a new push means a line there too.

**Adding a call**: a function in the group it belongs to, its type in that group's `handlers` table, and — for a new group — a line in the `GROUPS` array of `api.js`. A call the table does not hold is *answered* `{"success": false, "error": ...}` by `reject` rather than aborted — aborting an incoming message sends nothing back, so the caller would sit out its whole interaction timeout. `dev/plans/ws-accounts.md` is the plan the group was built from, with the previous implementation at commit `6c0d18a` (a single `src/server/ws.js` then); everything in it is built now. The old code read a config shape (`ws.emails`, `ws.features.*`) that `config.js` no longer accepts, so do not paste it back untouched. `dev/docs/websocket.md` is the protocol reference from the socket up — the communicator's frames, flags, syncs and timeouts, then the application API — and the one place the wire format is written down; `dev/plans/README.md`'s status table still says accounts are open, which is behind the code.
- `building.js` — the client build (see below).
- `zip.js` — a small zip reader and writer over `node:zlib`, the only thing that packs the desktop clients. `readZip` hands back every entry with its bytes **still deflated**, and `writeZip` streams a zip out of entries that are either copied over like that or given as `data`/`path` and deflated here, a few at a time on the thread pool. Plain zip only: it throws on zip64, on an encrypted entry, and when the output would pass 4 GB.
- `common.js` — shared helpers (`getArg`, `checkArg`, `getVersion`, `generateId`, `binarySearch`, `isDirEmpty`, `setAbsolute`, `httpsGetText`/`httpsGetImage`). `serverScriptPath` points at `./src`, and every client path is derived from it.
- `localization.js` — the server's i18n module, a fork of the client one that kept `translateHTML` where `src/client/web/src/localization.js` has moved to `add`/`translate` (both `load` a dictionary file). `ws/mail.js` is its one user: `loadDictionary` hands it `localization.json` through `load`, and the mail is built with `get`, `putParameters` and the `supportedLanguages` getter. `get` has no language fallback of its own — a language the dictionary does not hold comes back `undefined` — so the fall-back to English is `mail.js`'s. `translateHTML` walks `document` and is never called on the server. `localization.json` beside it holds the account-deletion mail, and `tests/localization.test.js` checks its language coverage.
- `communicator.js`, `mime.js` — vendored, see Licensing.

### Client build flow

**Nothing serves `src/client/web` directly.** `compileClients()` builds into `./tmp`, and the HTTP server only ever serves that output, so a change to the web client is invisible until you rebuild it — run `npm run server -- --compile` (a boot with an existing `tmp/web/index.html` and no `--compile` skips the build entirely).

The build minifies with `UglifyJS` for JS and **hand-written character scanners in `building.js`** for CSS/HTML — there is no minifier dependency for those. A file that fails to minify is copied verbatim with a warning rather than failing the build.

The desktop zips are packed by `zip.js`, not by a library: an Electron dist that is already a `.zip` is copied into the output entry by entry **without going through deflate again**, and only the files that are new — the web client, the Electron shell, the native libs — are compressed, in parallel through native `zlib`. That is what keeps a full compile at a few seconds instead of a minute and a half; the cost is about 1% on the size of the zip, because the dist keeps whatever compression it arrived with. JSZip was measured against this on `win32-x64` and dropped: it deflates through pako, in JavaScript on the main thread, which takes ~39 s on the 206 MB of native libs (~14 s at level 6, ~5 s at level 1) where `node:zlib` on four threads of the pool takes ~2.6 s — a full compile of ~42 s against ~4.5 s. Output:

- `tmp/web/` — the minified web client, plus a generated `index.json`. It is listed in `GENERATED_FILES` and skipped when copying sources; `buildConfFile` is the only thing that writes it (the one other thing the build writes into a client file is the default palette, into the `appearance` meta of `index.html` through `buildPaint`/`injectAppearance`), for the web client and every desktop zip in one go, and **nothing rewrites it at boot** — a client is only ever handed the config of the build it is part of, so it cannot fail its version check against the server it was built by. Change an address in the configuration and the clients see it at the next `--compile`, not at the next boot. It is the only generated file — `version`; an `http` and a `ws` section each holding the `domain` and `port` that server is reached at (the two are configured apart and may differ, and each is the `proxy` of its section where one is configured rather than the address it listens on); `appearance`, the `http.appearance` block as configured (`{}` when there is none); and `clients`, the `<os>-<arch>.zip` names this compile is about to write, which is what the downloads screen offers.
- `tmp/desktop/<os>-<arch>.zip` — an Electron dist from `./bin/<os>-<arch>[.zip]` with its `default_app.asar` stripped, repacked with the web client, the Electron shell, the matching `src/client/native/<os>-<arch>` libs, and `index.json` under `resources/app` (`Electron.app/Contents/Resources/app` on darwin). A target is only built when both a `bin/` dist and a matching native lib folder exist.

`./bin` and `./tmp` are gitignored (placeholder files aside) — the Electron dists are not in the repo.

### Client (`src/client/web/`, `src/client/electron/`)

**`.claude/CLIENT.md` is the client's reasoning** — why the shell, the overlay holders, the display scaling, the permission model and the user model work the way they do, and which modules are inert pending `dev/plans/`. The client sources carry one- and two-line comments only; read `CLIENT.md` before changing any of it, and put new explanation there rather than back into the source.

Plain ES modules, no framework, no dev build step, no bundler — the loader is `import()`. The web root holds the four files the whole application starts from — `index.html`, `index.css`, `index.js` and `index.json` — and nothing else but the `src/`, `ui/`, `libs/` and `media/` folders. `index.html` holds four elements and nothing else: the shared overlay, the loading dialog, and one surface per segment — `<main id="screen-main" data-segment="management">` and `<main id="room-main" data-segment="room">`, the second starting hidden — plus, ahead of them, the inline script that paints the theme before the first paint, and in the head the `appearance` meta the build writes the server's default palette into (see `.claude/CLIENT.md`, "The theme is painted before any module runs"). That is what has to exist before the first module can be fetched. The two surfaces are the same beercss grid area and the router hides one of them, so the room takes the whole window once the bars are off screen. Every bar, screen and dialog, the two navigation bars included, is a UI module mounted at runtime. **They are all built at boot, not lazily**: `buildUI` in `ui/ui.js` walks the whole `registry.ids()` list before the router runs — one dot-depth at a time, so `settings` is mounted before the `settings.appearance` that mounts into its markup, and a module that throws is logged and skipped rather than taking the boot with it. The tree is small enough that per-module laziness only bought a wait on the first click of each, and the router needs the chrome in the document anyway to be able to hide it. The UI is two segments and a layer over them — `management`, which owns that chrome and the screens the bars lead to (`new`, `devices`, `shares`, `services`, `downloads`, `login`), and `room`, which mounts into its own surface and takes the whole window; the loading dialog covers whichever segment is open, from boot until the server answers and again the moment the connection drops. A piece of shell chrome names its segment with `data-segment`, the router puts the open segment's chrome on screen and takes the rest off, so new chrome needs no router change. Everything else is a UI module under `ui/<layer>/<name>/` holding its own `index.js`, `view.html`, `view.css` and `localization.json`, all four fetched in one round trip when the module is built — `ui/ui.js`, the shell layer the modules are mounted by, is the one script in `ui/` that is not one of them, and a `localization.json` sits at every level that uses one — `ui/`, `ui/loading/` and `ui/management/` carry the shell's own slices, which no module brings. `index.json` is fetched at runtime and is server-generated — never hand-edit it.

- `index.js` (~100 lines) is boot alone, in five stages: the environment (`applyScale`, `initDesktop`, DOM ready), the configuration (local conf, then `applyTheme`/`applyLanguage`), the shell (the `ctx` it builds `createUI` and the `Router` around), the whole UI through `buildUI`, then the connection — and the loading layer only lifts once `loadPath` has the route on screen under it. Everything boot does to the document lives in `ui/ui.js`: `applyScale` (the root font size, from the display — every length in the shell is a rem, so that one number is the size of the whole UI; it is set again on a resize), `applyTheme` and `applyLanguage` (the local appearance and language settings) and `applyLocal` over both (the two plus what the desktop shell is told — boot's one call, and the settings reset's), `createUI` (the shared overlay and the rest of the `ctx["ui"]` namespace, closing over a `ctx` whose `router` is filled in after) and `buildUI`. The loading layer itself is `createLoading` in `ui/loading/loading.js`, which `createUI` hands the overlay to.
- `src/` — the core, functions only, in three folders that follow the two segments of the shell: the common scripts at the top level, `management/` for what the management segment runs on (`joins.js`, `account.js`) and `room/` for the room's (`room.js`, `stream.js` and the five files beside it). At the top: `env.js` (browser detection, plus the display metrics `applyScale` is built on — `getDisplay`/`getDisplayKind`/`getRootFontSize`. A CSS inch is 96 px by definition, so `screen.width / 96` is the *apparent* size the platform believes in, already divided by the viewing distance it assumes; a phone and a monitor come out right on their own and only a television does not, so a set is scaled and everything else keeps 16px. A set is identified by its user agent alone — `pointer: none` + `hover: none` is what a browser with no input device reports too, headless Chrome at 1280×720 included, so the guess only ever goes towards the desk size), `conf.js` (index.json + the IndexedDB local config, including the joins a user holds), `desktop.js` (the Electron `require()` block, only evaluated under the desktop shell: it asks the main process for the app path, loads the three desktop libs from it — `libs/auto-launch/auto-launch.js` and `libs/ffmpeg-chunkifier/encoder-ffmpeg.js` from `src/client/electron/libs/`, and `libs/easy-control/easy-control.node` from the native folder — onto `ctx["desktop"]` and then sets `globalThis.require` to `undefined`, so nothing loaded after it can reach Node), `server.js` (the `Server` transport class: the socket lifecycle, `conf-get`, the pairing, join and account calls, and the server-initiated messages it hands on as events), `localization.js` (the localization core, functions only: the dictionary starts empty and `load(url)` fetches one slice — boot loads the shell's level slices through `loadDictionaries` in `ui/ui.js` before anything asks for a line (`ui/localization.json` for `main.name`, `ui/loading/` for the loading layer, `ui/management/` for the `main.*` chrome), and each module's slice is `add()`ed by the registry; `supportedLanguages` is a getter, since the languages arrive with the slices; two dictionary lines carry a bold run of their own, so `escapeHTML` is what a name or an address coming from the server goes through before it is substituted into one), `view.js` (the `View`/`Panel`/`Screen`/`Dialog` contract), `registry.js` (the route table and the module cache), `router.js` (the `SEGMENTS` table, path → module, history, the delegated click handler; `navigate(path, params)` carries what the flow knows and the path cannot hold, which does not survive a reload). Under `management/`: `joins.js` (the remembered devices this client holds, on both sides of them — `ctx["joins"]`), `account.js` (`ctx["account"]` — the accounts this client is signed in as, kept in the local configuration with the session key that signs each in again, and which of them the client *is*: `resume()` on every `online` presents the wanted one before the route is drawn, `switchTo`/`logout`/`update` are the user menu and the account dialog, and `isGuest()` is what `permissions.isGuest()` in `ui/ui.js` answers from). Under `room/`: `room.js` (`ctx["room"]` — the live connection between this device and the other one: one `RTCPeerConnection`, one `control` data channel **wrapped in a `Communicator` the way the socket is** — so packets, acks and reassembly are the same on both legs, `send()` is one call with one behaviour, and neither has a message size to stay under — plus a `video` channel beside it, unordered and unreliable and wrapped in nothing, that `sendFrame()` hands a chunk to and the `frame` event reports; and the `connecting`/`connected`/`closed`/`message` events the shell draws from, opened by the server's `room-open` rather than by hand. It stands in one of two modes — **direct**, or **relayed** through the server when the two ends cannot reach each other, taken after `DIRECT_TIMEOUT` or on an ICE failure and only where `guestAllowRelay` allows one; `send()` and `sendFrame()` are the same calls either way and the room bar says which it is), `stream.js` (`ctx["stream"]` — what crosses the room: the host's screen as raw encoded frames and the peer's input back, **never a WebRTC media track**; it follows the room's `connected`/`closed` on its own, runs ffmpeg under the desktop shell and WebCodecs in a browser, and decodes in `stream-worker.js`, which draws through `stream-draw.js` — WebGPU, WebGL or 2D, the first that opens. `frame.js` is the wire format and the reassembler, pure and tested in `tests/frame.test.js`; `stream-ffmpeg.js` builds the ffmpeg lines, `stream-input.js` reads the peer's mouse and keyboard off the canvas and owns `pictureBox`, the letterbox mapping between the element and the picture inside it. `cursor.js` is the host's own mouse pointer: the capture is told not to draw it into the video, the host reads it with easy-control instead - in either of the two layouts `Mouse.getIcon()` is built to report, since the addon vendored under `src/client/native/` predates its own source in `dev/control/` and hands over packed pixels with no alpha - and sends the shape as a PNG and the position as it moves; the peer draws it over the canvas while it watches, and hands it to its browser as the canvas's own CSS cursor while it drives. `clipboard.js` is the one clipboard the two machines share while the room bar's switch is on - this machine's own clipboard behind one interface, the Electron one under the desktop shell and `navigator.clipboard` in a browser, and the echo between the two ends settled inside it; the peer's switch, the host's watch over its own clipboard and the `clipboard`/`clipboard-text` messages that carry it are `stream.js`'s. `stream-enhance.js` is the stage between the decoder and the drawer: the enhancements the room bar ticks — `upscale`, `interpolate`, `extrapolate`, any number at once — each an ONNX graph under `media/models/` run through ONNX Runtime Web (`libs/onnxruntime/`, fetched only once one is on) on WebGPU or, failing that, WebGL, and refused with a hint on a browser with neither; the three graphs are **mocks** written by `model/mock/make_mock_models.py` — the shape of the real thing with real GPU work and a picture that stays right — so the pipeline can be run and timed before a trained model exists. `.claude/CLIENT.md`, "The stream" and "The enhancer", is the reasoning).
- The client is always a user: it starts as the **guest**, and signing in adds an account beside it rather than replacing it — the accounts and their session keys are `accounts`/`userId` in the local configuration, not a user's row, since they say who this *client* is. Every user's records are rows of the one `user` table in the local IndexedDB, keyed by the id of the user they belong to; the guest is the row under the **empty id** (`GUEST_ID` in `src/conf.js`, reached through `getUser`/`setUser`/`resetUser`), since a client is only ever one guest and the empty key collides with no account. The `configuration` table is not a user's row, which is why a guest reset leaves the theme and the language alone. There is no signed out state and no second menu for one — `ui/management/nav-top/` keeps one user menu - the switch-account submenu, the account dialog and the sign out - whose avatar and check follow the current user, and its sign out means `resetUser("")` (forget the guest's name and local connections, behind a confirmation, `join-disconnect` on the server, and the route redrawn as a new guest) for the guest and a server session for an account. The account dialog shows a different column per user: the guest gets its name (`account.guest`) and a delete that is that same sign out (`account.reset`), an account the information, sessions and delete windows. The switch-account submenu is drawn from `ctx["account"]` on every `change` it emits, and a switch or a sign out redraws the route under the dialogs that go, since a screen gated on the guest permissions was drawn for the user before.
- `ui/` — three folders, one per layer of the shell, and `ui.js` over them: `loading/` (the layer over both segments — `loading.js` and the `version/` dialog that replaces it), `management/` (the two bars, the `menu`/`search` dialogs of the small layout, the screens the bars lead to, the `connection` dialog one connection is named and forgotten in, the `confirm` dialog every delete is asked through, and the `settings`/`account` dialogs), `room/` (the room screen's own files, the `loading` and `exit` dialogs it waits and asks with, the `create`, `joining` and `request` dialogs of the flows into it, and `settings` — a `room-settings` dialog that is markup and an empty class today, nothing opens it). Below that, one folder per screen or dialog, and a nested folder is a nested module mounting into its parent's markup: the five settings windows (`appearance`, `audio`, `video`, `control`, `about`) land in `#settings-windows`, the five account windows in `#account-windows` — `information`, `sessions` and `delete` for an account, `guest` (its name) and `reset` (its sign out) for the guest, the dialog showing the column of whoever the client is — which is why the build order follows the dot-depth of the registry id. A module folder may hold helper scripts beside its `index.js` that are not modules themselves: the `*-box.js` card builders of `devices`, `shares` and `account/sessions`, `login/google.js` (the Google button) and `settings/media-devices.js`. **A registry id is not its path**: `room-create` lives at `ui/room/create/`, and the id is what the shell, the markup and the router know it by.

The module contract: default-export one class extending `Screen`, `Dialog` or `Panel` with `static id`, `static rootId` (the id of its own markup) and `static mountPoint` — plus `static segment` for a screen that does not belong to `management` — and `mount(ctx)` / `open(params)` / `close()`. A module never imports its own markup or strings: the registry entry names its `view.html`, `view.css` and `localization.json`, fetches the three in parallel with the script, merges the dictionary slice and translates the fragment before it reaches the document. `ctx` — `{server, conf, joins, account, room, setLocal, resetLocal, getUser, setUser, resetUser, localization, router, desktop, ui}` — is the only way a module reaches anything outside itself; a module that has to talk upward dispatches an event on itself. Adding a screen means a folder under the layer it belongs to, a line in the `registry.js` route table (**literal** `import()` specifiers only, so `tests/assets.test.js` can see them) and a `data-route` attribute in the markup — it never touches `index.js`.

Layout: `index.html`, `index.css`, `index.js` and `index.json` at the web root, the core under `src/`, the UI modules under `ui/`, every image and sound under `media/` (and the ONNX graphs under `media/models/`, an asset like an image), vendored browser libs under `libs/`. Assets are referenced by root-absolute path (`/media/icon.svg`, `/ui/management/new/view.html`) — the build preserves the source layout and walks it recursively, so a new module folder needs no build change and a path that resolves in the sources resolves in `tmp/web`. The Electron shell serves the same tree over `local://`, so its own asset paths (`media/icon-32.png` for the tray) must track any move too.

`src/client/electron/` is `main.js` (the shell), `package.json` (what Electron reads for the entry) and `libs/` — the vendored CommonJS `auto-launch` and `ffmpeg-chunkifier` that `src/desktop.js` requires by path; the whole folder is copied into the zip as `resources/app`, minified in script mode. The Electron shell registers a privileged `local://` protocol that serves the bundled web app from the app path (so the desktop client can reuse the web client verbatim), exposes a small IPC API to the renderer, and manages the tray plus a single-instance lock. Note the three known holes in `main.js`, all of them development settings that have to go before a release: **the main window is opened on `https://localhost`, not on `local://local.local/`**, so a packaged zip loads whatever a dev server is serving rather than the client inside it (`createMainWindow`'s default argument — the comment above the call still names the intended URL); `ignore-certificate-errors` is switched on, which is what makes that address work against the self-signed certificate in `conf/`; and the `local://` handler does not guard against paths escaping the bundle.

`src/client/native/<os>-<arch>/libs/` holds `ffmpeg/` (prebuilt binaries) and `easy-control/` (the input addon — ViGEmClient on Windows, CoreGraphics/IOKit on macOS, where `easy-control.node` links `GamepadImplement.a` — a dylib despite the name — through `@loader_path`); the `libs/` level is there so the folder lands beside the shell's own `libs/` in `resources/app` and `desktop.js` reaches both under one prefix. `dev/control/` is the addon's source — the maintainer's `easy-control` (node-gyp, `binding.gyp`, its own `package.json` and README, a dev server for testing it by hand), rebuilt there and its `.node` copied into `native/`; nothing in the Node app builds it. `win32-x64` and `darwin-arm64` exist today, so those are the two buildable desktop targets; a dist in `bin/` is matched by Node's platform name (`darwin-arm64.zip`, never `macos-…`). `dev/bin_building.txt` is the checklist for preparing one (drop `default_app.asar`, the Windows icon through `dev/win_icon_changer/`, `xattr -cr` and an ad hoc `codesign` on macOS). `.DS_Store` and the like are dropped by `isJunkFile` in `building.js` from every copied folder.

### `model/`

A `uv`-managed Python project (pinned to 3.14, Torch from a CUDA 13.2 index) for the video upscaling and frame-generation work: `upscale/`, `frame_gen_intra/`, `frame_gen_extra/`, each with a `summary.md` of where it stands, and `model/README.md` over the three. Separate from the Node app; nothing in `src/` calls it. What the client *does* run is `mock/make_mock_models.py`'s output — the three stand-in graphs it writes into `src/client/web/media/models/` — and a trained model replaces a mock by being exported under the same name with the same input and output (float32 NCHW in [0, 1], `N`, `H` and `W` symbolic — the client runs every tile of a frame as one batch; `input` for the upscaler, `previous` and `current` as two inputs for the two-frame models; `output` the same shape, or twice it for the upscaler).

### `dev/`

Nothing under it runs as part of the app. `docs/websocket.md` (the wire protocol), `plans/` (designs, with `README.md` as the index — see the note under Adding a call), `control/` (the `easy-control` addon source), `rollup/` (the vendoring helper), `mysql_docker/` (a MySQL + phpMyAdmin container for exercising the `mysql` database type against the `better-sqlite3` default), `win_icon_changer/` and `bin_building.txt` (preparing an Electron dist for `bin/`).

## Known server defects

None outstanding. The six that stood here were fixed together; what follows is
what each one taught, so the shape does not come back.

- **A request handler must not throw.** `httpRedirectHandler` read
  `req.headers.host.split(":")`, and an HTTP/1.0 request carries no `Host`: the
  `TypeError` was an uncaught exception in a handler, which ends the process,
  from the one port that is open in plaintext. The header is also attacker
  text, so it is matched against `HOST_NAME` before it reaches a `Location` and
  `http.domain` stands in for anything missing or malformed.
- **A promise started ahead of its `await` needs a handler now, not later.**
  `writeZip` runs up to `CONCURRENCY` deflates in front of the writer. Parked in
  `pending[]` bare, one that rejected early was an unhandled rejection and took
  the process with it, which is what made the `try`/`catch` around
  `writeDistZip` unreachable for the failures it exists for. They are settled
  into `{value}`/`{error}` on creation and re-thrown in the writer's order, and
  a `finally` drains whatever is still in flight.
- **Never build over the name something is served from.** `writeDistZip` writes
  `<target>.zip.part` and renames onto the target only once the zip is whole,
  removing the part file on failure; `compileClients` still catches and moves on
  to the next target, but a half-written client is no longer offered as a
  client.
- **`--help` is a promise.** The usage line advertised `-c, --configuration
  <path>` while `getArg` was inline-only, so `--configuration ./x` matched
  nothing and silently booted the default configuration. The CLI now has one
  rule per form (see Commands above), `--help` states it, and `checkArg` fails
  the run on the wrong form instead of falling back.
- **Closing the connections is not closing the server.** `ws/ws.js` `stop()` calls
  `wsServer.close()`, so in shared-port mode the `upgrade` listener comes off
  the HTTP server rather than staying on it; the `wsHttpServer` close sits
  outside the `wsServer !== null` branch, so a `start()` that failed between
  creating that listener and assigning `wsServer` no longer leaks the port.
- **A cache index is a claim about a disk that keeps changing.** `buildCache`
  is re-run by every `refreshCache` from a fresh listing rather than walked
  once at boot: a file created since (a `view.css` added to a UI module and
  compiled in) used to 404 for the life of the process, and a deleted one went
  on being answered out of memory. Access history survives a rebuild, since it
  belongs to the file rather than to the scan. Beside it: a 304 carries
  `notModifiedHeaders` and so no `Content-Length` for a body that is not
  coming, `isDownloadable` gives both request handlers the same rule for
  `tmp/desktop`, and `refreshCache` admits a file only if it fits the byte
  budget instead of stepping over it with the last one.

## Code conventions

Follow the surrounding file: `"use strict"` at the top, imports grouped and commented as internal / third-party / first-party, `const name = function() {}` over declarations, bracket access with string keys for config and message objects (`conf["ws"]["port"]`), double quotes, 4-space indent, and a module footer exporting both named and default (`export { a, b }; export default { a, b };`).
